# 운영 보완 및 검증

## 인증

- 로그인·가입·비밀번호 변경은 동일 이메일 15분 20회, 동일 IP 15분 100회로 제한합니다. 실패·성공을 포함한 시도 수이며 계정 존재 여부를 제한 응답으로 구분하지 않습니다. 초과하면 HTTP 429와 Retry-After를 반환합니다. 메모리 키 공간은 제한하며 로그에 이메일·IP·비밀번호를 남기지 않습니다.
- 가입·새 비밀번호는 영문·숫자 포함 12자 이상입니다. 기존 시연 비밀번호를 자동 변경하지 않았습니다. 로그인 상태의 비밀번호 변경에는 현재 비밀번호 확인이 필요하며 현재 서버의 동일 사용자 세션을 종료합니다.
- `production` 프로필은 시연 계정 차단, Secure 쿠키, 127.0.0.1 바인딩이 없으면 시작을 거부합니다. 새 운영 관리자는 실제 이름·이메일을 받은 뒤 계정을 별도로 지정해야 합니다. production에서는 기존 시연 관리자도 로그인할 수 없습니다. 로컬 시연은 유지합니다.
- 시도 제한·세션 취소는 단일 서버 메모리 기준입니다. 재시작 시 제한이 초기화됩니다. 서버를 여러 대 운영하면 공유 제한·세션 저장소 또는 프록시 제한과 계정 세션 무효화 정책을 추가해야 합니다. 프록시 전달 헤더는 신뢰할 수 있는 프록시만 덮어쓰도록 구성합니다.

## DB 장애·재시도

- 연결 설정: Oracle 접속 5초·소켓 읽기 15초, JDBC 쿼리 10초, 트랜잭션 기본 30초, Hikari 획득 10초입니다. 드라이버·서버 상황에 따라 실제 해제 시간은 달라질 수 있습니다. 브라우저는 25초 후 결과 미확인으로 안내합니다.
- 연결·트랜잭션 장애는 HTTP 503, 쿼리 시간 초과는 504, 제약·동시 처리 충돌은 409로 구분합니다. 응답에는 SQL·연결 문자열·계정·비밀번호를 넣지 않으며 로그는 오류 종류와 조회용 reference만 남깁니다.
- 저장 응답을 못 받았다고 실패로 단정하지 않습니다. POST 자동 재전송은 하지 않고 내역 확인을 안내합니다. 새 화면은 동일 선택을 다시 제출할 때 sessionStorage에 보존한 UUID를 사용합니다. 서버는 APP_USER 잠금과 RENT_REQUEST의 기존 고유 신청번호를 이용해 같은 키·내용에 기존 항목 ID를 반환합니다. 키를 바꾸거나 로컬 저장소를 삭제하면 새 신청으로 취급합니다. 레거시 API의 키 없는 호출에는 이 보장이 없으므로 외부 연동도 requestKey를 전달해야 합니다. 상태 전이는 기존 버전 검사로 중복 적용을 막습니다.
- 공유 Oracle의 실제 네트워크를 끊지 않습니다. 두 번째 쓰기에서 연결 예외를 주입한 트랜잭션 롤백 시험, 실제 Oracle의 동일 키 재시도, 브라우저에서 저장 성공 응답을 의도적으로 버린 뒤 재시도하는 시험을 구분해 수행합니다. 실제 소켓 단절·DB 재시작·커밋 결과 불명 상황 시험은 별도 시험 DB에서 진행해야 합니다.

## 조회 성능

`/api/state?page=0&size=25&view=all`은 전체 건수·pageInfo와 최신 페이지를 반환합니다. size는 1~100, view는 all/current/history입니다. Oracle 11g ROWNUM 방식으로 신청 ID를 먼저 제한하고 해당 페이지의 로그·출고·원래 선택을 묶어 읽습니다. 학생 조회는 모든 쿼리에 본인 조건을 적용합니다. 학생 진행/과거 내역·관리자 목록에 이전/다음 페이지를 제공합니다. 예약 가능 검사에 필요한 공개 예약은 페이지와 별도로 조회합니다.

현재 DB에서 페이지 분리·소유권·조회 개수와 읽기 전용 응답 시간을 확인합니다. 대량 더미 행을 공유 DB에 넣거나 인덱스를 임의 생성하지 않습니다. 대량 데이터 부하 시험·실행 계획 분석은 격리한 복원 DB에서 수행하고 필요 인덱스 DDL을 별도 검토합니다.

2026-11-18 로컬 앱→현재 Oracle 조회 측정: 당시 전체 신청 항목 28건, 크기 10/25/100의 반환은 10/25/28건이었습니다. 각 3회 측정 중앙값은 약 121/156/178ms, 기본 25건의 최대 응답은 약 20KB였습니다. 최초 연결·네트워크·데이터량에 영향을 받는 소규모 측정이며 운영 용량 보장은 아닙니다. `tools/check-performance.ps1`은 로컬 시연 관리자만 사용하고 결과에는 계정·신청 내용·세션 토큰을 기록하지 않습니다.

## 상태·로그·백업

- `/api/health/live`: 앱 응답 상태, DB 장애와 독립합니다. `/api/health/ready`: SELECT 1 FROM DUAL 결과만 UP/DOWN·200/503으로 반환합니다. 설정·계정·오류 상세는 노출하지 않습니다.
- `tools/check-health.ps1`은 live/ready/catalog의 소수 읽기 요청을 측정해 p50/p95와 응답 크기를 출력하고 `.work/health-results.json`에 저장합니다. 대량 부하 시험은 아닙니다. 프록시에서 상태 조회 빈도를 제한하고 모니터링은 30~60초 간격으로 구성합니다.
- 기본은 콘솔 로그이며 운영 systemd 환경은 journald로 수집합니다. 파일 로그를 선택하면 외부 설정에서 `logging.file.name`을 쓰기 가능한 별도 경로로 지정합니다. 파일당 10MB·전체 100MB·7일 회전 설정을 추가했습니다. HTTP 본문·SQL 바인딩·인증 헤더 로깅을 활성화하지 않습니다.
- DB 백업은 외부 DB 관리자가 권한과 저장 위치를 정해야 합니다. 목표 복구 시점·소요 시간, 백업 주기·보관 기간·암호화·접근 권한을 확정하고 작업 로그를 남깁니다. 애플리케이션 JAR 백업은 DB 백업을 대신하지 않습니다.
- 복구 훈련은 별도 빈 스키마/DB에 백업을 복원→`ops/backup-check.sql`로 객체·건수·상태 비교→시퀀스 충돌 여부 확인→격리된 앱에서 가입·신청·승인·출고·반납 검증 순서입니다. 복원된 개인정보와 시연 계정의 접근도 제한합니다. 운영 스키마를 덮어쓰거나 설치 SQL로 복구하지 않습니다. 백업·실제 복원은 아직 실행하지 않았습니다.

## 런타임 업그레이드 검토

현재 Java 8·Spring Boot 2.7.18·ojdbc6·Oracle 11g XE를 유지하여 학교 DB 호환성을 보존했습니다. Spring Boot 2.7.18은 2.x의 공개 지원 종료 버전입니다. [Spring 공식 안내](https://spring.io/blog/2023/11/23/spring-boot-2-7-18-available-now/). Spring Boot 3.5는 Java 17 이상을 요구합니다. [공식 요구사항](https://docs.spring.io/spring-boot/3.5/system-requirements.html).

Oracle은 드라이버·JDK·DB 버전별 호환표를 제공하므로 최신 드라이버로 단순 교체하지 않습니다. [Oracle JDBC FAQ](https://www.oracle.com/database/technologies/faq-jdbc.html). 운영 환경은 패치된 JDK와 유지보수 가능한 Spring·DB/JDBC 조합을 결정하고 격리 환경에서 인증·잠금·시간대·타임아웃·재시도·전체 업무를 검증한 뒤 전환합니다. 현재 변경만으로 공개 서비스의 보안 검토를 완료한 것은 아닙니다.

사용자 과업 시험은 사용자가 일부 진행했다고 알려주었으며 실제 결과 수치·참여자 기록은 전달받지 않아 문서에 임의로 기입하지 않았습니다. 운영 관리자 지정·HTTPS 설치·외부 배포는 실제 대상 정보 확정 후 수행합니다. Commit/Push는 별도 승인 후 진행합니다.
